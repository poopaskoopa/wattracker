Step 5 of the android client plan (#197): the activities list and ride detail.

Both backends (cloud and local desktop) drive the same screens on the shared `ReadSession` seam — the local backend gets the screens for free, the way it did for the dashboard.

## What's in the branch

1. **PR #419's post-merge follow-up** (approved in its re-review: "test `removeDevice()` against `tests/vectors/removal_decision_v1.json` … then update the Android cell in `docs/mobile-parity.md`"). The #410 rule is extracted from `removeDevice()` into `CloudSession.removalCompletesLocally(status, serverDateMillis, now, tolerance)` — mirroring the iOS static. `RemovalDecisionVectorTest` reads the vector unmodified (23 cases), parses each `Date` header with the transport's own `parseHttpDate` (so "unparseable means absent" is checked end to end), and asserts the session's decision for every case. The Step 4 cells in the parity matrix now read "Done (#419)". (Small items from the same review: this clone's git identity is now `taksmon <…@users.noreply.github.com>`, and the stale "KSP coupled to Kotlin" comment is fixed.)

2. **The bounded activity detail/stream cache** (iOS #351/#358 parity, required by the #197 matrix row). `CloudSession`'s ride-object memory is now: capacity 8 (one detail + one stream per ride kept open), least-recently-used eviction that prefers streams (the larger payload), a 5-minute age bound (the refresh protocol carries no independent detail/stream revision), and per-ride generations plus the activities route's revisions tracked in `reconcile()` — a ride whose revision advanced (or that was tombstoned) loses its cached copies, and a read that raced the advance is served but not stored. Pair / sign-out / removal clear all of it. Six new `CloudSessionTest` cases trace the cap, the TTL bound, and the eviction through the request log.

3. **The ride display model** (`screens/activities/RideDisplay.kt`): a line-for-line port of the iOS `ActivitiesModel.swift` half — `RideSummary` (newest first, the object-id fallback for the numeric id), the formatters (durations half-to-even as on the desktop; the ride card's `05:09` vs the zone formatter's `5:09`), `ZoneGroup`/`ZoneRow` (the server's `duration` string preferred, the local formatter as fallback), `StreamSeries`, `ChartAxis`/`ChartTicks` (nice 1/2/5×10ⁿ ticks, zero-based, negatives extending the floor, no clipping), `MinutesClock` (the cloud `time` channel is effectively all nil: with the ride duration the samples spread over 0…duration, else 1 Hz — the 86-minute regression), and `CombinedChartSeries` (altitude behind on its own min…max band, power on the left "W" axis, HR + cadence sharing the right "bpm / rpm" axis). `RideDisplayTest` ports the iOS `RideDisplayTests` case for case (15 tests).

4. **The view models.** `ActivitiesViewModel`: rides newest first; tombstones absent from the state entirely (the cutoff hides server-side — nothing is greyed); the cache paints before the network; a changed identity (pair/sign-out/removal) clears the previous rider's rides and supersedes the load in flight while a same-identity resume joins it; pull to refresh lifts a cold-start gate; a local 429/503 earns the rate-limit notice. `RideDetailViewModel`: detail and streams in parallel, failing independently; a streams 404 — cloud `Failure.Server(404)` or the local backend's `Http(404)` — and a payload with no plottable channel both map to the rider-facing "No recorded streams" (the #445 publisher contract); the header's summary comes from the cached list so the metrics paint before the network answers. 18 tests against a scripted `ReadSession`.

5. **The screens and navigation.** The list (date, duration, distance, average, NP, IF, TSS, RPE — the iOS row's metrics; lazy rows, so a long history does not hold itself in memory at the UI layer), the detail (summary, zone times, the "Ride graphs" chart with the tappable legend that hides series without rescaling the plot), and the layout decision the issue asks for, stated in the code: **on the wide, short viewports (a phone in landscape, any tablet) the list and the detail sit side by side** — width is the axis that is not scarce there and push navigation would cost the rider a round trip on the scarce one; **in a phone portrait the detail is pushed as its own screen** (a plain push, so the back button returns to the list; the rail/drawer still highlights Activities). Pull to refresh, the "Offline" badge, and the "updated" stamp behave the way the dashboard's do.
